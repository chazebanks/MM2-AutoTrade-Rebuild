## Why a standalone request test instead of loading the old rotator?

The original Stage51 `pdiddler3_outgoing_ROTATING_v18_REACHABLE.lua` automatically rotates all eligible players; `SendAttempts=3`; it can physically tap multiple cards and **automatically decline incoming** requests. That is UNSUITABLE for the first physical send experiment. Also, Stage87's contact permit deliberately authorizes *starting a request conversation only*, not item offer or final acceptance. Do not copy old numeric checker aliases, outdated +15 profit floor, source pricing assumptions or unknown settlement claims into this pathway.

## New isolated implementation

`pdiddler/new_part4/STAGE89_ONE_TARGET_ONE_REQUEST_DIAGNOSTIC.lua` deliberately requires BOTH explicit `PDIDDLER_STAGE89_ONE_REQUEST_ARMED=true` and `PDIDDLER_STAGE89_TARGET_USERNAME=` the **exact current Roblox username** of ONE intended partner in the **same server**. Best first native test is a consenting account, not an arbitrary public player. No auto target selection, automatic card opening, rotation, hopper, incoming Decline, pending Cancel, offer placement, withdrawal, final Accept, trading-value processing or Discord.

- The operator must **manually open that ONE player's MM2 leaderboard Profile/Trade popup**, after the original Stage51 scanner (already native-read-only-tested in Stage88) has recognized an eligible target. The script validates exact current player object, `Players:GetPlayerByUserId`, exact popup `Container.Username`, current `Container.Action.Trade` GuiButton, visible frame and button geometry. DisplayName/fuzzy aliases never prove player identity.
- Loads immutable pinned original T4 scanner, Stage88 contact-specific price-safe view, and real Stage87 contact P3 and outgoing evidence controller. Market profile explicitly `isFresh=false` and repricer returns nil. The scanner's own `getOwnInventory`/ `getVerificationState` give typed local evidence; `controller:authorize(target)` then `controller:prepare(target, token)` must pass at the exact input boundary, including fresh own inventory, partner fingerprint, job/GUI/session binding.
- Refuses if any other script/transaction owner, pending outgoing/incoming request, preexisting item trade GUI, mismatched/ambiguous leaderboard, unproven scanner partner, changed current client/target object, stale own proof or changed card. **Only ONE** physical `VirtualInputManager:SendMouseButtonEvent` down/up gesture on verified Trade button after rechecking both popup and prepared contact token. Reserves `requestTapCount=1` BEFORE dispatch; an input failure or missing pending UI is `UNCERTAIN`, never a retry. No cancel, auto decline or Accept.
- Observes (without clicking) up to 8 seconds for exact-target *client* `SendingRequest.Username` or a trade-window presence (the latter does not establish partner). Even a matching local pending UI is **NOT proof** the MM2 server accepted the request or any trade completed. Reports ONE aggregate `[GINGERSCOPE STAGE89 SINGLE REQUEST]` JSON, no private username, UserId, weapon items, inventory, source price, webhook or transaction claim.
- Device environment remains a separate hypothesis: the snapshot and Lua5.4 mocked GUI do not prove Delta can send a physical Trade tap or that Roblox will process it. The scanner's listeners cannot be safely unloaded; use a new server before any rerun.
