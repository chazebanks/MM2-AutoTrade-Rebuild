## Why this stage exists

Real user test Stage63 on MAIN iPad observed `AcceptTrade(false)` followed by `AcceptTrade(true, TABLE_1)` in a stable trade GUI, plus one own eligible-copy gain across two consistent post-close reads. The user confirmed a **manual ALT→MAIN one-sided transfer visibly finished, with a Claim Weapon prompt, and the weapon appeared in MAIN's inventory**. This is operator-confirmed client evidence; it is NOT a unique, independently server-authenticated settlement identifier or verified profit. [Stage63 user evidence](https://github.com/chazebanks/MM2-AutoTrade-Rebuild/pull/115#issuecomment-6730976215) and [operator completion confirmation](https://github.com/chazebanks/MM2-AutoTrade-Rebuild/pull/115#issuecomment-6731118005).

Stage63 +1 therefore did **not** independently bind the exact raw key of the gained weapon to the client callback's one received row. Archived [MM2 v1456 TradeModule](https://github.com/tlredz/decompiledGames/blob/0552a0f3502217a1cf89df66be9bd0f153e47fa4/murder-mystery-2/v1456/ReplicatedStorage/Modules/TradeModule.lua) calls `ItemPopupService:AddNewItem(item[1], item[3], item[2])`, with archived [PopupService type parameters](https://github.com/tlredz/decompiledGames/blob/0552a0f3502217a1cf89df66be9bd0f153e47fa4/murder-mystery-2/v1456/ReplicatedStorage/ClientServices/ItemPopupService.lua) `string,string,number`. **Current live item-row element semantics are unknown**, and the old source is historical reverse-engineering, not server documentation.

## One engineering question, no automatic trading

During ONE ordinary manual trade on MAIN, can we demonstrate **strict private primitive equality** of the callback's purported received weapon key and the only raw `Weapons.Owned` key increasing by exactly 1, with unchanged two post-close full raw maps? Emit ONLY a boolean/status and element type labels, **never any raw key, weapon name, account, JobId, secret, actual price, raw table, or item instance**.

Even a positive `CLIENT_RAW_RECEIPT_EQUALS_OWN_GAIN_UNATTRIBUTED` establishes exact string equality in *client-supplied readbacks*, not independently authenticated item-key semantics, server transaction, unique item instance, offer revision, cause, counterparty consent, profit or learning authority. `tradeOutcome=UNKNOWN` and **all** final auto Accept, completed/rejected Discord learner, completed webhook and realized profit flags permanently FALSE. ## Implementation architecture and regression safeguards

1. `pdiddler/new_part4/STAGE66_ROLE_NEUTRAL_PRIVATE_RAW_SNAPSHOTS.lua`: strictly additive fork of Stage59 role-neutral read-only core (ancestor commit `54b97f65290ce038910436e27600be6a2c4a005e`, blob `e1324b...`). The **same scanner, same GetProfileData calls (one baseline, two postclose)** and same known-good legacy Stage9/28/29/30 observation modules. Rather than another RPC or monkey-patching `scanner.getOwnInventory`, it privately parses the scanner's already-calculated, sorted `inv.seen` array of `tostring(rawId).."x"..qty` built from the **full `Weapons.Owned` map**, with full map total and fingerprint reconciliation. Rejects unsafe raw IDs, bad quantities, missing/ambiguous keys, sparse tables and foreign metatables; no snapshot printed, logged, sent or serialized. Stores three maps only in memory under its experiment owner while the source is active. **Known uncertainty**: `tostring(rawId)` conversion and the scanner's data origin are client claims; no external server-authentication property.
2. `pdiddler/new_part4/STAGE66_READONLY_ACCEPT_PRIVATE_RAW_EQUALITY.lua`: standalone one-MAIN wrapper adapted from the user-tested Stage63 runner. Starts exactly ONE passive `Trade.AcceptTrade.OnClientEvent` listener before the pinned core. Requires stable bound GUI/partner/job, one `BOOLEAN_FALSE` callback followed by one `BOOLEAN_TRUE` callback with a TABLE_1 within five seconds, GUI closure, exact safe baseline and two completed own-inventory readbacks. For the true callback it reads **only** first row fields 1,2,3 in memory to note type labels; it NEVER includes their values in output. Calls separate pure Stage65 helper on the in-memory copied row and raw full map snapshots and serializes only the returned proof status. Additional callbacks, ambiguous GUI, stale owner, missing helper/core, mismatched raw quantity/item category, or new server context fail closed.
