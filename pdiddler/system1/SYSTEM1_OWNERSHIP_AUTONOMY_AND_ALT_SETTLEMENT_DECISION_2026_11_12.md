Date: 2026-11-12 America/New_York. Source: operator direction after public-lobby P3 discussion. Status: **architecture/test-order decision only; no live capability or final Accept enabled here**.

## Nonnegotiable objective
The desired finished product is an *unattended, autonomous* inventory-growth trading system pursuing Gingerscope. "No autonomous final Accept in the present test build" is a **current verified capability/rollout flag**, NOT a permanent prohibition on implementing or testing automatic Accept. The purpose of controlled ALT testing is precisely to develop and prove automatic behavior in bounded circumstances so it can later be promoted into a separately risk-limited public trading runtime. The operator does NOT need to manually act as the bot during every test; one deliberate ARM authorizes a **specified budgeted automated test**.

Do **not** treat all autonomy as one binary flag:
- **TEST_AUTO_MECHANICS**: operator arms once, original P3 automatically sends requests and P4 automatically performs *preapproved* offer/withdraw/decline mechanics, continuously fail-closed, **no final Accept**; actual 8/8 ALT iPad CLIENT PASS is closed.
- **TEST_ALT_SETTLEMENT_MANUAL_BASELINE**: consenting MAIN and ALT complete a deliberately inexpensive trade manually on both sides; independently capture before and after inventories for BOTH accounts, matched exact item/quantity/variant, late Claim/confirmation interactions, and repeated clean profile reads after rejoin. We can have strong *persistent inventory corroboration*, but without privileged authoritative game-server receipt cannot describe a client observation as cryptographic/authoritative server settlement.
- **TEST_ALT_AUTO_FINAL_ACCEPT**: separately scoped future test after first establishing the manual baseline and adequate identity/offer mutation safeguards. Explicit one-time operator ARM, exact consenting ALT UserId/object, cheap sacrificial inventory and quantity budget, max 1 test trade, exact side snapshots/offer-revision change invalidation, lock on unknown acceptance state, operator STOP, no new request after fault; exercise the P4 automatic final Accept/confirmation path with clean post-trade dual-client inventory reconciliation. Not yet implemented. Do not activate the existing disabled Accept button by flipping a single flag without implementing and testing complete transition safety. Repeat negative simulations first.
- **TEST_PUBLIC_P3_ROTATION**: public server with bounded player scanning/normal game trade requests only, 3 distinct Player IDs max per operator ARM, no offer/Accept, no spam/duplicate request, verified pending cancel before moving on. This uses **Part 3** and does not require a second personally controlled ALT. It can be performed *after* other subsystem work according to the operator's stated order.
- **AUTONOMOUS_PUBLIC_TRADING_RELEASE**: eventual product mode. The user may preapprove budgeted economic/risk policies once (not each offer); automatic runtime can then act under those limits. Requires sufficiently dependable true item identity, stable active offer state, cross-side completion reconciliation, fresh permitted economic data or proven independent valuation methodology, tested recover/rollback, inventory protections, user-approved risk budgets and a separately reviewed deployment decision. Current code/test evidence **does not establish** those prerequisites. Keep default disabled until they are demonstrably satisfied.

1. **Part 1** `pdiddler/pdiddler1.lua`: bot-heavy/suspicious server *classification/approval*. Returns true or false; **does not teleport**.
2. **Part 2** `pdiddler/pdiddler2.lua`: Tablet selector and optional friend Play; **not player contact, hopper or trader**.
3. **Part 3** scanner `pdiddler3_scanner_MODULE_v6_5_PART4_STATUS_BRIDGE.lua` plus current supervised `system1/pdiddler3_outgoing_single_send_epoch.lua`, original P3/P4 coordinator and watchdog: eligible player classification, one-by-one request/ignored 15-second pending-cancel proof, incoming handling, processed targets, next-player rotation, join/leave, exact client trade-open handoff. **Do not rebuild these in Part 4.**
4. **Part 4** original protected IO/observer/controller: inside a *bound active trade*, GUI/variant/quantity/slot reconciliation, safe offer/revoke/replan/decline, and eventual automated final Accept + settlement observation after independent controlled ALT verification. P4 owns integration with System2 portfolio planner and System3 evidence/learning after source/settlement gates. No current unrestricted Accept.
5. **Server hopping**: a *separate runtime/orchestration integration* must respond to Part1 server-quality decisions and Part3 verified queue exhaustion. Part3 owns player rotation within the server and signals when exhausted; its reviewed P3 fork has **no TeleportService/hop execution**. Do not invent or misattribute an existing installed hopping executor. Rejoin/hop must not occur with a pending request, live trade, uncertain side effect or unreleased P4 lease.
