# Stage50 — ONE same-window read-only pre-offer profile/raw UpdateTrade key correlation

## New evidence question, based on actual earlier native results
Real Stage43/44 iPad results established a bounded CLIENT-only `UpdateTrade` actor-relative Batwing key triple, with manual ADD then REMOVE; they did **not** read the real own `GetProfileData().Weapons.Owned` in that SAME GUI window. Stage49 offline pure Lua code verified that key equality is possible but has NO real iPad sample. Actual scanner source establishes that `Sync.Weapons` raw keys, `Weapons.Owned` keys and scanner's `tostring(rawId)` rows exist, but a Supreme checker ID is assigned through aliases/fuzzy scoring. Therefore even a successful live raw-key match **cannot validate Supreme checker ID or unique copies**.

**One Stage50 hypothesis:** In a stable, manually opened empty trade, one fresh *client-returned* own profile dictionary might contain an EXACT same-Lua-type raw key as the unique `Sync.Weapons` Batwing candidate, which a separate later `UpdateTrade` client callback reports in the LocalPlayer's own one-Batwing Offer row. Manual Batwing ADD then REMOVE gates remain identical to successful Stage44.

## Exactly one new RPC and timeout
The new `STAGE50_READONLY_PREPROFILE_OFFER_KEY_PROBE.lua` forks (does NOT modify) the earlier Stage44 read-only passive observer, uses the existing immutable Stage9 reader/contract and same Stage39–44 pure key/state/actor inspectors, and loads pinned new `p4_stage50_preprofile_raw_key.lua`. After exactly one visually empty trade with uniquely verified bound partner/root, a unique `Sync.Weapons/Sync.Item` Batwing candidate and stable GUI binding, it makes **ONE** `Remotes.Inventory.GetProfileData:InvokeServer()` call with **NO parameters** for the **local account only**. The method is the same legitimate read-like inventory method already present in the project's current scanner, NOT an offer/trading mutation. Roblox's [official RemoteFunction API](https://create.roblox.com/docs/reference/engine/classes/RemoteFunction) says `InvokeServer` **YIELDS**; this diagnostic calls it in its own worker with a 6-second observer deadline, no retries and no blocking the main observer forever. A timed-out worker may remain pending in the engine until the RPC completes, but it cannot publish or mutate the state after timeout/finish, and a second read is prohibited.

The reader rejects missing/changed player, JobId, GUI/root, offer signature, **transient slot visibility/text or child insertion/removal during the RPC even if it reverts before the next poll**, wrong/duplicate partner, acceptance, unknown profile nested schema, malformed raw Owned map, numeric/string printable key collisions, zero or insufficient raw copies, bad quantities and stale/ambiguous/duplicate UpdateTrade callbacks. It stores raw profile and raw Sync key only in private local closure, never reports them. The pure Stage50 profile inspector prints only fixed enum/boolean flags; no original item key/username/user ID/job/token/URL/content/raw count is exported. After this read succeeds, prints `[STAGE50] PROFILE_BOUND_READY / LISTENING_UPDATE_TRADE`; operator may then manually place ONE Batwing in **DELTA YOUR** offer, waits `ADD_MATCHED_CLIENT_ONLY`, manually REMOVES that same Batwing and keeps both offers empty. No final Accept on either account. Diagnostic prints one `[GINGERSCOPE STAGE50 PREPROFILE KEY CORRELATION]` anonymized report and disconnects every listener.

Only if the pre-offer raw key and the later single bounded UpdateTrade add/remove client states correspond does it report `stage50ClientRawOfferOwnedMatch=true` and `TWO_PHASE_CLIENT_PREPROFILE_RAW_KEY_MATCHED`. This is **one CLIENT observation on one account** — it does NOT guarantee an exact server trade-session nonce, callback delivery causality, unique item instance, verified page/checker ID/variant, partner-owned inventory, trade success or profit.
