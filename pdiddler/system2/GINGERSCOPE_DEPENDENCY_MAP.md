# Gingerscope dependency map

The engineering backlog is [gingerscope_requirements.json](gingerscope_requirements.json). Its source revisions identify the evidence checked for each requirement. The dated November 25 matrix records the standalone baseline.

## Supported qualification architecture

`python -m pdiddler.gingerscope qualify` runs the full controlled sequence on the desktop. The Python coordinator owns configuration, Supreme archive admission, economics, recommendations, SQLite and the receipt. It launches Lune 0.11.1 for the controlled Luau mechanics. The Luau process runs against in-memory inputs and returns versioned, two-sided observations for Python validation. A separate CPython process from the authorized private checkout consumes the settled synthetic evidence from that same exercise. The private response contains counts and verdicts. The [offline guide](GINGERSCOPE_OFFLINE.md) specifies dependency versions, commands, stop and resume behavior, and the report location.

| Boundary | Contract and owner | Failure behavior |
|---|---|---|
| Startup and dependency validation | CPython 3.12, SQLite with JSON support, pinned project dependencies and Lune 0.11.1. The coordinator selects the explicit historical clock and isolated work area. | Missing dependencies or incompatible source revisions stop before qualification. A partial public-only run identifies the missing private stage. |
| Luau to Python | Versioned JSON links one controlled session to exact inventory and offer observations. The transport carries only fixture data. Python validates sequence, revision, identity and quantities before advisory evaluation. | Missing or malformed observations, incompatible schemas, stale revisions and unsupported identities fail closed. A Lua receipt carries controlled provenance. |
| Intelligence and storage | Supreme archive identity, separate accounts, lease ownership and offer revision define the scope of each calculation. Python owns both bilateral directions, search bounds, policy, portfolio revisions and transaction deduplication. | Market, inventory or offer changes retire prior current advice. Invalid input and interrupted sessions fail before a real gain or a real learning label can be recorded. |
| Public to private | Only the qualification-owned synthetic evidence and explicit exercise inputs cross to the private learner. The existing client-only V2 ingestion pins retain their own provenance and scope. | Missing private checkout, unsupported source revisions, fabricated evidence and real/synthetic scope mismatches cannot establish a passing full run. |
| Operator receipt | Progress identifies the running stage. The final sanitized JSON reports stage verdicts, bounds, exact revisions when verified, environment and evidence scope. The optional copy target is an owned, new report file. | Stop or failure carries its own status. A subsequent run opens a new isolated exercise. No live state or private source material is copied into the receipt. |

The current candidate uses the desktop as its supported host. Historical Lua modules remain source-pinned regression and controlled observation inputs. A supported native observation producer for the current MM2 client and an authoritative real outcome producer remain distinct dependencies. Their capability, participation and evidence criteria are in the [supervised validation gates](GINGERSCOPE_SUPERVISED_VALIDATION.md).

The Lune exercise uses the checked-in health and Part 2 code, the P3 startup supervisor and rotation coordinator, the P3/P4 handoff, supervised TradeIO, the native market capture and the pinned Supreme-only protected adapter and hash implementation. It supplies in-memory scheduler and client-service inputs, scanner rows, request outcomes and GUI observations. The controlled startup uses the optional-prompt-absent Part 2 path. The separate Part 2 regressions retain prompt and readiness coverage. Python admits the result using `system2/controlled_host.py`. This keeps the production economics and mutation rules in their existing owners and confines the desktop emulation to the host inputs.

| Qualification stage | Execution and handoff |
|---|---|
| 1 and 2 | Application startup, dependencies and the reviewed Supreme archive precede controlled client startup. Inventory observations and the bound controlled session cross the versioned JSON boundary. Python preserves distinct accounts and validates canonical identity and quantities. |
| 3 | The same inputs drive candidate generation, two-sided evaluation, arbitration, growth search, downside and concentration checks, and protected advisory recommendations. |
| 4 | The Python session lease binds offer observations and evaluations to the same input revision, checks the Luau economic observations against the Python results, and invalidates advice after changes. Separate decline, interruption and unknown outcomes exercise terminal behavior. |
| 5 | Two simulator witnesses corroborate an eligible current synthetic offer. The state owner reconciles the inventories and deduplicates the settlement through reopen. Private evidence processing applies the real-evidence exclusion gate and the synthetic learner's eligibility rules. The refreshed inventory drives a subsequent advisory evaluation. |
| 6 and 7 | Lease recovery, application replay, market expiry and changes, production input rejection and state failure cases cover recovery and adversarial behavior. Resource measurements apply to the reported desktop workload. |

## Supported path and ownership

| Producer or owner | Contract | Consumer and failure boundary |
|---|---|---|
| Offline entry `pdiddler/gingerscope.py` | Bounded, validated JSON, explicit command, clock and state scope | Runs advisory review, long-run scenarios, controlled session replay, state configuration, revision history and comparisons, recovery, and Supreme capture and comparison. Current-clock analysis requires an unexpired trusted Supreme archive. Controlled session replay uses an isolated synthetic store. The market capture command only writes original publisher pages for independent review. |
| Supreme archive reader and edition comparison | Immutable archive identity, publisher edition and capture/expiry, exact category and publisher ID, descriptive metrics and quoted ranges | Portfolio summary, offer evaluation, planning and state synchronization. Untrusted values or a different provider cannot substitute for a valid Supreme archive. |
| Manual inventory and Part 3 contract | Separate accounts, exact item identifiers, nonnegative inventory revisions, explicit unknowns and one lease for the account | Portfolio and session entry. Unpriced assets remain explicit and cannot enter a proposal. Publisher identifiers cannot establish native item-instance ownership. |
| Controlled Part 4 contract | Session, sequence and offer revision, both sides' quantities and physical slots, event kind and provenance | Evaluator and state record. A changed inventory, edition, offer, lease or expiry invalidates applicable advice. The controlled bridge consumes manual observations without game-side action or transport. |
| Bilateral evaluator and Part 5 planner | Known available quantities, one Supreme edition, two sides' arithmetic, separate slot/copy burdens, protected alternatives and bounded routes | Advisory arbitration and operator review. Explicit counterpart stock is a scenario input. Listed demand, paper ranges and route feasibility carry no acceptance or empirical liquidity claim. |
| Long-run strategy scenario | Explicit sequential market editions, counterpart stocks, unavailable opportunities and selected deterministic baselines | Track market revaluation, price coverage and hypothetical trade growth across six independent measurements. Cumulative published downside is conditional on complete ranges. |
| Local application store | Versioned database, edition and inventory revisions, evaluation bindings, versioned configuration, leases and outcome evidence | Historical accounting, idempotent replay and recovery. Schema version 2 transactionally migrates version 1 and retains unresolved records. Closed or client-only observations cannot create realized gains. Corroborated synthetic settlement remains isolated. |
| Public V2 adapter and private intake | Staged V2 body, private transport binding, strict session/revision fields and immutable gate inputs | Private archive and aggregate analyzer. Client responses do not prove authoritative settlement. Public tests use isolated synthetic fixtures. |
| Offline learning | Validated features and outcome provenance, source/feature timing and scope, versioned train/holdout metrics | Separate private model evaluation with evidence gates, sealed metadata, saved artifacts and explicit rollback selection. Real-world learning remains gated on adequate independently attributed records. |
| Development continuity | Immutable project metadata, policy and selected historical source blobs | Developer recovery and release review. Application leases, evidence and restart state belong to the local application store. |

## Source selection and evidence

- The supported Python path is independent of historical Luau launchers. The old Part 4 launcher and rotating balancers retain rules such as forced highest opener, minimum listed gain and stale pricing for historical evidence. MM2Values, hybrid and third-party price sources are archived or diagnostic only.
- Protected native fixtures explicitly load original pinned Stage9/83/101 roots. The frozen five-scenario host and November 25 research variants use distinct versioned dependencies. The whole-system workflow stages original sources into a scratch runner and checks Git blobs before executing fixtures.
- The private analyzer pins public commit `5da551192aaf6e438786bfad800e434b30c6a666`. The intake and learning gate are byte-identical at the public baseline to the private analyzer pins `20d8a0e8fda75c10a7101b242bfbd9a00d20cb7f` and `eaf22abce32eba3bfe2c4e1f42dec6cf89c498e7`. The controlled application evidence path preserves that staged V2 contract. A separate synthetic contract passes settled revision records from the actual SQLite state into the private learner without using V2 records as verified settlements.
- Reproducible selected-family regression uses Python 3.12, Hypothesis 6.170.15, Lune 0.11.1, Lua 5.4 and archived dependencies listed in the whole-system workflow. Source pins for continuity and legacy launchers live in `continuity/manifest.json` and the relevant fixture and CI scripts.
- The pre-integration rollback references are public `2622777c47c7913a2b9097efc9d8c6283e7ba04f` and private `18648765aaa8b6a41e0fd86aba9e7baeb97f586f`. The first integrated revisions are public `4bf114925baca83bbc2017347eb9be4ae84ff375` and private `1c98c0889d327ca913a7da40fd50d741ea6c45b2`. Public main at review was `44268df1e3080b49aa9e586851867fd602a3ce1f`. Existing draft ancestors and historical receipts remain available. The continuity gate's historical coverage remains partial.
- The immediate qualification rollback points are public `f7b4ff33f4015315a26f41d3c6ed812e7711032c` and private `026e8865d09066c358288a7239598ec6a088fba9`. Restore a backed-up database to a separate path before using older source. Use the rolling checkpoint for the final exact-head qualification and GitHub evidence.
- The November 25 direct parity receipt verifies its pinned edition against the publisher and retains the original expiry. The baseline exact-head runs establish scoped offline verification. Current native observation, independent settlement, real learning and release approval require their own evidence.
